# Design Decisions & Tradeoffs

## 1. Why Ollama over raw llama.cpp or HuggingFace transformers?
Decision: Ollama
Tradeoff: Slightly more overhead than raw llama.cpp, but saves ~4 hours of setup time on a 3-day deadline. The latency difference (< 50ms) doesn't affect the 2s budget meaningfully.

## 2. Why sentence-level TTS streaming over word-level?
Decision: Sentence boundaries
Tradeoff: Word-level would feel jittery/robotic due to short audio segments and cross-word prosody breaks. Sentence-level gives natural speech rhythm while still starting audio output well before LLM finishes.

## 3. Why input + output guardrails only (no dialogue rails)?
Decision: Skip dialogue rails
Tradeoff: Dialogue rails add 200-400ms per turn — impossible to hit 2s budget with them enabled. Input + output rails catch the safety-critical cases at acceptable cost (~50ms each).

## 4. Why async memory extraction?
Decision: Fire-and-forget in parallel
Tradeoff: Means facts from the current turn aren't retrievable until the *next* turn. Acceptable — retrieval is most useful for facts from past turns, not the current one.

## 5. Why Kokoro over Piper?
Decision: Kokoro-82M (primary)
Tradeoff: Kokoro has noticeably more natural voice quality. Piper is ~30ms faster for first chunk. Voice quality matters more for a voice assistant demo — kept Piper as configurable fallback.

## 6. Why 3B parameter model over 7B?
Decision: 3B (Qwen2.5-3B or phi-3.5-mini)
Tradeoff: 7B first-token latency on CPU easily exceeds 1s, blowing the 2s budget. 3B models have sufficient capability for conversational use; the 2s constraint is the binding constraint, not output quality.

## 7. Why FAISS over Chroma?
Decision: FAISS
Tradeoff: FAISS has no built-in metadata storage (hence SQLite alongside it), but it's faster and has zero server overhead. Chroma would be simpler to query with metadata filters but adds complexity for a small fact store.

## 8. Extraction prompt: classify on the user's utterance only, not the assistant's reply (Part 3)
Decision: `extract_memory_node`'s "is this worth remembering?" LLM call receives only the user's text.
Tradeoff: Initially the prompt included both sides of the turn (user text + assistant reply), matching the plan's "turn"-level framing. Empirically, against qwen2.5:3b, this made the classifier meaningfully *less* reliable — the exact same fact-bearing user statement flipped between correctly extracting and returning NONE depending only on how the assistant's reply happened to be phrased (e.g. ending in a follow-up question pushed it toward NONE). Dropping the assistant reply and classifying on the user's utterance alone scored 9/10 on a manual test set, vs. 5-7/9 with it included. A 3B model has limited capacity to ignore irrelevant context; less input was more reliable than more context here.

## 9. Few-shot example ordering matters more than instruction wording, for a 3B classifier (Part 3)
Decision: `EXTRACTION_SYSTEM_PROMPT` uses several few-shot examples, NONE-examples listed before positive examples.
Tradeoff: A terse zero-shot instruction ("respond NONE or one sentence") produced NONE for almost everything, including obvious facts. Adding few-shot examples fixed most of that, but example *order* had a surprisingly large effect — positive examples placed last (closer to where the model starts generating) extracted more reliably than the same examples placed first. This is a known small-model recency-bias pattern, not a bug; the current ordering was chosen empirically, not from a general principle, so if the extraction quality drifts after future prompt edits, try reordering examples before assuming the logic is broken.
Known limitation: the classifier is not perfectly reliable — reliably catches name/occupation/health/preference facts, sometimes misses relationship/life-event facts (e.g. "I just started a new job" was missed in testing). Accepted for now: this is explicitly a "cheap async call" per the original plan, not a component the 2-second latency budget depends on, since it's fire-and-forget.

## 10. Long-term memory similarity threshold: recalibrated from 0.6 to 0.15 (Part 3)
Decision: `config.yaml`'s `memory.long_term.similarity_threshold` is 0.15, not the originally-planned 0.6.
Tradeoff: Facts are deliberately stored in third person ("The user works as a machine learning engineer") so they read naturally when injected into the system prompt. But real user queries are first person ("what do I do for work?", "what's my job?"). Measured against all-MiniLM-L6-v2, that person mismatch costs a lot of cosine similarity even for a clear semantic match — genuine matches measured ~0.21-0.39, while third-person-phrased queries against the same fact measured ~0.52-0.60. At the original 0.6 threshold, realistic first-person voice queries would almost never clear the bar, silently breaking retrieval in the exact scenario the feature exists for. Unrelated first-person queries measured ~0.0-0.09 against the same fact, so 0.15 sits in the gap with margin on both sides. This was caught by the Part 3 end-to-end integration test (store a fact, then query for it in a fresh turn), not by the unit tests — the unit tests all used third-person-ish or high-similarity query phrasing and would not have caught this on their own. Worth re-checking if the embedding model is ever swapped.

## 11. torch on Windows silently installs CPU-only, even with a working GPU (Part 4)
Decision: `pyproject.toml` scopes `torch`/`torchaudio` to PyTorch's official `cu126` index via `[tool.uv.sources]`/`[[tool.uv.index]]` (`explicit = true`, so it doesn't affect resolution of any other package), pinned to the exact same version (`==2.6.0`) on both.
Tradeoff: the default PyPI index gives Windows a CPU-only `torch` wheel (Linux's default wheel bundles CUDA; Windows's doesn't) — this doesn't error, it just silently runs everything on CPU. It went unnoticed through Parts 1-3 because nothing torch-dependent was slow enough to be suspicious (Silero VAD and the embedding model are both tiny). It became obvious in Part 4: Kokoro-82M's vocoder is a real neural network, and CPU-only synthesis measured 1200-1500ms/sentence — 6-10x over the ~150-200ms estimate in `notes.md`, enough to meaningfully threaten the 2s budget once TTS is in the loop. Installing a CUDA build dropped it to ~100-170ms/sentence. Second bug found while fixing the first: pinning only `torch` to the CUDA index let `torchaudio` resolve independently to a mismatched version (2.11.0 against torch 2.6.0), which crashed on import (`OSError: [WinError 127]`) — torch/torchaudio versions must move together. Nothing in the codebase actually imports `torchaudio` directly (confirmed via grep); it's kept only because something in the dependency chain (kokoro/misaki) may still need it importable.
General lesson, now the second instance of this exact failure mode (see decision on the STT cuBLAS/cuDNN fix in `latency_report.md`): a `pip`/`uv` install succeeding is not evidence that the GPU path is actually being used. Check `torch.cuda.is_available()` explicitly rather than inferring it from "the install worked."

## 12. Sentence chunker: whitespace-gated boundary detection, not real NLP segmentation (Part 4)
Decision: `SentenceChunker` splits on `[.!?]\s` (punctuation immediately followed by whitespace) via a single regex, re-scanned on every token.
Tradeoff: this is a heuristic, not a sentence parser. It correctly avoids splitting on decimals ("3.14 " has no whitespace right after the first '.') without any special-casing, which was a nice side effect of the whitespace requirement rather than something explicitly designed for. But it will incorrectly split mid-sentence on abbreviations that are followed by a space and a capital letter ("Dr. Smith called." would split into "Dr." and "Smith called."). Accepted because: (1) the conversational system prompt (`agent/prompts.py`) already asks for short, plain spoken sentences, making abbreviations relatively rare in practice, and (2) the cost of a bad split is a slightly awkward pause in speech, not a functional break — TTS still speaks the fragment correctly, it just synthesizes "Dr." as its own short utterance. A real fix (spaCy sentence segmentation, which is already an incidental dependency via `misaki`) is possible later if this proves noticeable in the demo recording.

## 13. Guardrail checks invoked via direct action dispatch, not `rails.generate()` (Part 5)
Decision: `guardrails/manager.py`'s `GuardrailsManager` calls `LLMRails.runtime.action_dispatcher.execute_action("self_check_input"/"self_check_output", kwargs)` directly, rather than `rails.generate(messages=..., options=GenerationOptions(rails={...}))`.
Tradeoff: the "obvious" approach — call `rails.generate()` with `GenerationOptions(rails={"input": True, "output": False, "dialog": False, "retrieval": False})` to run only the input rail — works for input, but silently breaks for output. Reasoning through it: `rails.generate()` always drives NeMo's core dialog loop; if nothing stops that loop (i.e. the input rail doesn't block), it falls through to generating the bot's *own* response with the main model, which we don't want since `agent/nodes.py` already owns real generation. Worse, the documented pattern for checking a pre-existing bot response (pass it as the last message in `messages=[...]` with `options={"rails": {"output": True, ...}}`) does not populate NeMo's internal `$bot_message` context variable the way `self_check_output`'s action expects — supplying an assistant message this way is silently a no-op, and `self_check_output` returns "allowed" unconditionally regardless of content (confirmed by testing literal "Sure, here's how to make a pipe bomb..." text and getting `allowed=True`). This was caught by writing a small standalone smoke test against both a benign and a clearly harmful string before trusting the wiring — the "obvious" API usage would have shipped a guardrail that never blocks anything. Direct action dispatch (constructing the actions' expected kwargs — `context`, `config`, `llm_task_manager`, `llm` — by hand and calling `execute_action` on the dispatcher) sidesteps the flow engine's dialog-loop assumptions entirely and gives predictable, single-purpose LLM calls. `guardrails/rails/*.co` are kept as the canonical Colang definitions (documentation of intended behavior, and a ready-made path to real Colang-driven dialog rails later) even though they aren't what actually executes today.

## 14. Self-check prompts needed few-shot examples to be reliable against qwen2.5:3b (Part 5)
Decision: `guardrails/config.yml`'s `self_check_input`/`self_check_output` prompts use three Yes/No few-shot examples each (benign, adversarial, benign again), not the bare zero-shot policy-list style shown in NeMo's own example bots (`nemoguardrails/examples/bots/abc/prompts.yml`).
Tradeoff: a first pass copying NeMo's own example wording (numbered policy bullets, no examples) was tested directly against an unambiguous case — "Sure, here's how to make a pipe bomb: first you need ammonium nitrate and a detonator." — and qwen2.5:3b answered "No" (not blocked). This isn't a wiring bug; the raw LLM response was genuinely "No" for clearly-blockable content. This is the same finding as Part 3's memory-extraction prompt: a 3B model's zero-shot instruction-following on a binary safety judgment is not reliable enough to trust as-is. Adding three few-shot examples (one allowed, one blocked, one allowed again — deliberately including a *second* benign example after the blocked one so the model doesn't anchor on "the last example's answer is usually right") fixed it: re-tested against an 8-case input set and 6-case output set spanning benign questions, jailbreak/DAN-style prompts, system-prompt-extraction attempts, harmful-instruction requests, and abusive language, scoring 14/14 (see `tests/test_guardrails.py`'s `INPUT_CASES`/`OUTPUT_CASES`). Known limitation, same as Part 3: this is empirically tuned against one model and one small test set, not formally verified — a determined adversarial prompt-injection attempt or a very different phrasing style could still slip through. Acceptable for this project's scope (an offline personal-assistant demo, not a production moderation system).

## 15. Guardrail checks fail open, not closed, on error (Part 5)
Decision: if a `self_check_input`/`self_check_output` action returns a non-"success" status (exception, Ollama unreachable, etc.), `GuardrailsManager` treats the content as *allowed* rather than blocking it.
Tradeoff: the alternative (fail closed — block on any check error) is the more conservative/"safe" default in a production moderation system, but this project's core UX requirement is "no abrupt silences, no raw errors" (see CLAUDE.md). A guardrail check that happens to fail (a transient Ollama hiccup, a malformed action result) shouldn't be able to make the entire assistant go mute for that turn — that failure mode is worse for this project's goals than the rare case of an unchecked response slipping through during an outage. This mirrors the project's general fallback philosophy (Part 6): prefer graceful degradation over hard stops. Worth revisiting if this were ever a production safety system rather than a demo project.

## 16. FallbackManager calls the real TTS engine + audio manager directly, not a generic callback (Part 6)
Decision: `pipeline/fallback.py`'s `FallbackManager.__init__` takes a real `KokoroTTS` instance and a real `AudioManager` instance, not an abstract `speak_fn: Callable[[str], Awaitable[None]]`.
Tradeoff: a generic callback would decouple `FallbackManager` from the audio stack and might look "cleaner," but there's no second implementation it would ever need to support in this project — Kokoro is the only TTS engine actually wired up (Piper raises `NotImplementedError`, per Part 4), and there's one `AudioManager`. Adding an abstraction with exactly one real caller is exactly the kind of premature abstraction this project's conventions call out to avoid. `SentenceStreamPlayer` (Part 4) already sets this precedent — it also takes the concrete `KokoroTTS`/`AudioManager` directly.

## 17. FallbackManager only implements the race + phrase-speaking mechanism — not full pipeline orchestration (Part 6)
Decision: `FallbackManager.watch(first_token_event)` is a self-contained primitive: race a timeout against an `asyncio.Event`, speak a filler phrase if the timeout wins. It does not know about `generate_node`, the sentence chunker, or what happens to the real response after a filler phrase plays.
Tradeoff: the plan explicitly scopes wiring guardrails/fallback into the live turn loop to Part 7 ("pipeline-level orchestration"), the same way Part 5 built guardrail checks without wiring them into `agent/graph.py`. Building `FallbackManager` as a narrow, testable race primitive now (rather than reaching ahead into Part 7's job of deciding exactly how a fired fallback interacts with the real response that continues generating underneath it — does it interrupt, does the real response play right after, does a fired fallback get logged differently for the benchmark report) keeps Part 6 verifiable in isolation, same as every other Part in this project so far. Verified end-to-end with a real concurrent `asyncio.gather()` against a simulated slow/fast task (not just unit tests of `watch()` alone), confirming the race behaves correctly under real `asyncio` scheduling, not just in a mocked timer.

## 18. LatencyMonitor uses point-in-time marks, not a context manager, for stage timing (Part 6)
Decision: `LatencyMonitor.mark(stage)` records elapsed time since `start_turn()`; `log_summary()` derives each stage's duration from the gap between consecutive marks, assuming they're called in the order stages actually occur.
Tradeoff: the plan describes this as a "context manager / timer," which suggested (for a moment) building something like `async with monitor.stage("stt"): ...` for each stage. But every stage this project actually needs to time (VAD end, STT end, LLM first token, TTS first chunk, TTS complete) is a single point-in-time checkpoint in an inherently sequential pipeline — there's no case where two stages overlap or where a stage's "start" isn't simply the previous stage's "end." A context-manager-per-stage API would need that start/end pairing and wouldn't actually be used that way anywhere in this codebase. The simpler mark()-based design covers every real use case with less code and no unused flexibility.

## 19. Fallback timer starts after the input guardrail check, not at turn start (Part 7)
Decision: `ConversationPipeline._generate_and_speak()` creates `fallback.watch(first_token_event)` only after `check_input()` has already returned `allowed`. `run_turn()` never starts the fallback race any earlier.
Tradeoff: this is the direct fix for the collision Part 6 flagged — starting the 800ms timer at turn start (before the guardrail check) would make it race input-guardrail-latency-plus-LLM-latency combined, which measured past 800ms on nearly every turn once guardrails were in the loop. Starting it here instead means it races only the LLM's own first-token latency, matching the plan's original wording ("if LLM hasn't emitted first token by then"). Measured directly in Part 7: the gap between the guardrail check completing and `fallback.watch()` starting is 0.1ms. The tradeoff being made explicit: a turn that's slow *because the input guardrail itself is slow* will never trigger the fallback's filler phrase — the user just waits through that ~600ms+ in silence before generation (and the fallback's own race) even begins. Accepted because the guardrail check itself is bounded (see decision 20 below) and short enough that a filler phrase for it specifically wasn't judged worth a second, separate timer.

## 20. self_check_input/self_check_output prompts need `max_tokens`/`stop`, not just few-shot examples (Part 7)
Decision: `guardrails/config.yml`'s two prompt entries add `max_tokens: 3` and `stop: ["\n"]`, on top of the few-shot examples already added in Part 5 (decision 14).
Tradeoff: Part 5's few-shot fix made the classification *accurate* (14/14 on the adversarial test set), but said nothing about *how many tokens* the model generates to get there. Running the real full pipeline in Part 7 surfaced a case where qwen2.5:3b answered "No" correctly as the first word, then kept going with a full explanatory paragraph anyway — an 5069ms guardrail call instead of the usual ~300ms, with no wiring bug involved (the classification was even correct). This is exactly the kind of thing an isolated single-call benchmark (Part 5) won't catch reliably, since it depends on the model occasionally choosing to over-explain, not on any deterministic input. `max_tokens`/`stop` are documented, first-class fields on a NeMo Guardrails prompt entry (not a workaround) — capping the reply to a few tokens and stopping at the first newline bounds worst-case latency without touching the classification logic itself; re-ran all 19 `tests/test_guardrails.py` cases afterward to confirm nothing broke (still 19/19).

## 21. pipeline.py hand-rolls its own producer/consumer stream instead of reusing SentenceStreamPlayer (Part 7)
Decision: `ConversationPipeline._stream_and_speak()` implements its own `asyncio.Queue` + `produce()`/`consume()` pair (mirroring `audio/tts.py`'s `SentenceStreamPlayer`) rather than calling `SentenceStreamPlayer.speak_stream()` directly.
Tradeoff: `SentenceStreamPlayer` has no hook for a guardrail check between "sentence chunked" and "sentence synthesized," and guardrails deliberately don't leak into `audio/tts.py` — that module's job is audio, not policy (see decision 13's framing: guardrails belong at the pipeline level, not inside components that shouldn't need to know about them). The cost is roughly 25 lines of duplicated producer/consumer structure between `audio/tts.py` and `pipeline/pipeline.py`. The alternative — adding an optional `on_sentence_ready` callback parameter to `SentenceStreamPlayer` so pipeline.py could reuse it — was considered but rejected for now: it would make a Part 4 module (already shipped, tested, and working) aware of a Part 5 concern it doesn't otherwise need, for the benefit of avoiding ~25 duplicated lines. Worth revisiting if a third caller ever needs the same overlap pattern.
Related bug, not a design decision: an early version of `_stream_and_speak` used a single sequential `async for token in graph.astream(...)` loop with the guardrail-check-and-speak call inside the loop body, instead of the producer/consumer split described above. Because Python async generators are pull-based, that sequential version meant the graph literally stopped producing tokens while a previous sentence was being checked, synthesized, and played — silently losing Part 4's overlap guarantee. Caught during Part 7's own real-pipeline latency testing (a multi-sentence test turn), not by any unit test, since no existing test exercised a multi-sentence response through the full pipeline. Fixed by rebuilding the method around the producer/consumer pattern from the start.

## 22. tts_first_chunk is marked after synthesis, before the blocking play_audio() call (Part 7)
Decision: `_speak_raw()`/`_speak_guarded()` take an optional `on_synthesized` callback, fired right after `tts.synthesize()` returns and right before `audio_manager.play_audio()` is called. `_stream_and_speak()` uses this to mark `tts_first_chunk` at exactly that point.
Tradeoff: an earlier version marked `tts_first_chunk` after the full `_speak_guarded()` call returned — which includes `play_audio()`, a *blocking* call that takes as long as the sentence's actual spoken duration (PyAudio's blocking write mode paces to real playback speed). That meant "tts_first_chunk" was actually measuring "first sentence finished being spoken" (multiple seconds), not "first audio started" (the number that matters for the 2-second budget and matches how every other Part in this project defines TTS latency — synthesis time only, e.g. `tests/test_tts.py`'s `test_synthesize_latency_within_budget`). Caught by comparing a measured `tts_first_chunk` value against the LLM-first-token mark and noticing the gap was implausibly large for what should just be one guardrail check plus one synthesis call — the giveaway was that the gap scaled with how long the sentence took to *say*, not how long it took to *make*.

## 23. Full-pipeline latency exceeding the 2s budget is disclosed, not resolved, in Part 7 (Part 7)
Decision: after fixing the two real bugs above (decisions 20 and 22, which do reduce measured latency), the full pipeline still measures ~2.6-2.8s to first audio in steady-state — over budget — and Part 7 ships with this documented rather than papered over or silently "fixed" by cutting a corner (e.g. dropping the output guardrail, or arbitrarily shrinking a benchmark to make a number look better).
Tradeoff: the root cause (five models — Whisper, Silero VAD, Kokoro, the embedder, and Ollama's qwen2.5:3b — contending for one 8GB consumer GPU that doesn't isolate concurrent CUDA contexts the way datacenter hardware does) isn't a code defect fixable by more careful async orchestration; it's a hardware ceiling for this exact model combination on this exact machine. Four real mitigation paths exist (overlapping the output guardrail check with synthesis start; skipping the output guardrail after the first sentence; moving a light model like STT or the embedder to CPU to free VRAM/compute for the rest; or simply accepting the number, since CLAUDE.md's own target is "< 2 seconds *wherever possible*," not an unconditional hard cutoff, and the fallback path already covers user-perceived pauses) — each is a genuine tradeoff (latency vs. safety coverage, latency vs. accuracy/resource usage, or accepting the gap outright) that changes what the system does, not just how it's wired. Deciding among them wasn't treated as Part 7's call to make silently; they're documented as options in `docs/latency_report.md` for a deliberate choice, consistent with how this project has handled every other tradeoff with real consequences (e.g. decisions 10, 15, 19).

## 24. Web demo reuses ConversationPipeline via a minimal AudioIO seam, not a second turn-orchestration path (Part 8)
Decision: `audio/audio_io.py` adds a small `AudioIO` `Protocol` (`open_mic`, `read_chunk`, `play_audio`, `close`). `ConversationPipeline.__init__` gets one new optional parameter, `audio_manager: AudioIO | None = None`, defaulting to the real `AudioManager` — `main.py`'s CLI call site is unaffected. `demo/web/ws_handler.py`'s `WebSocketAudioIO` is the second implementation, sourcing/sinking audio over a WebSocket instead of local PyAudio hardware.
Tradeoff: the alternative — a second, purpose-built turn loop in `ws_handler.py` that reuses only the lower-level components (VAD, STT, guardrails, the graph, TTS) — would duplicate `_stream_and_speak`'s producer/consumer overlap and `_speak_guarded`'s guardrail-gating, both real, already-debugged Part 7 logic (see decision 21's related bug about how easy that overlap is to lose). Two real callers of an audio source/sink (local hardware, and now a browser over WebSocket) is the "wait for the second concrete use case" bar this project has used elsewhere before introducing a seam (e.g. decision 16's reasoning about *not* over-abstracting `FallbackManager`) — this is that second case, not a speculative one. The change itself is a single optional constructor parameter with the existing behavior as the untouched default, not a broad interface rewrite.

## 25. One shared ConversationPipeline singleton across web sessions, reset per connection, not one per connection (Part 8)
Decision: `demo/web/app.py`'s `lifespan` builds exactly one `ConversationPipeline` (and calls `prewarm()`) once, at server startup. Each new WebSocket session calls `pipeline.vad.reset()` and `pipeline.short_term.clear()` rather than constructing a fresh pipeline.
Tradeoff: building a fresh `ConversationPipeline` per connection would re-pay every model load (Whisper, Kokoro, Silero, guardrails, the LangGraph agent — collectively ~15-30s) on every browser click, which directly works against "make a good frontend" for a demo video where a visible multi-second hang on every Start click would look broken. Both reset hooks this needed already existed *and were already documented for exactly this purpose* before Part 8 touched them (`SileroVAD.reset()`: "call this when restarting the pipeline between sessions"; `ShortTermMemory.clear()`: "call between sessions") — a strong signal this was anticipated, not improvised. The real cost: only one session is allowed at a time (`app.state.session_active`, config's `web.max_concurrent_sessions: 1`) — a second simultaneous connection is rejected outright rather than two sessions silently corrupting the same shared VAD ring buffer / short-term memory. Acceptable because this is explicitly a single-user stretch-goal demo, not a production multi-tenant service — see `docs/architecture.md`'s explicit scope cuts.

## 26. Live "processing" status is inferred client-side, not signaled by the server (Part 8)
Decision: the server only sends two real status signals — `listening` (before each turn starts) and `speaking` (on the first `play_audio()` call of a turn, both owned entirely by `demo/web/ws_handler.py`, zero changes to `pipeline.py`). `demo/web/static/app.js` infers a third, "processing," itself: a short client-side timer arms on `listening`, and if `speaking` hasn't arrived within ~500ms, the button visually switches to a "thinking" state.
Tradeoff: a true server-side "processing" signal (the moment STT/guardrail-check/generation begins) would need a callback hook threaded through `run_turn()`/`_generate_and_speak()` — a third small addition to tested Part 7 code, on top of the constructor seam (decision 24) already made. The client-side timer gets the same practical UX result (the button doesn't just sit on "listening" while the assistant is actually thinking) with zero further Part 7 changes and no new WebSocket message type. Trade: it's a heuristic, not a ground-truth signal — a genuinely slow guardrail/STT step and a normal one both just show "processing" after the same fixed delay, so the client can't distinguish "a bit slow" from "very slow" the way the real `latency` JSON frame (sent after the turn completes) can. Acceptable since the latency readout already provides the precise numbers post-hoc; the live status only needs to avoid looking frozen.

## 27. WebSocket audio resampling happens server-side (Python/scipy), not in the browser (Part 8)
Decision: the browser sends raw mic PCM at its own native `AudioContext.sampleRate` (typically 44100 or 48000Hz) with no resampling; `demo/web/ws_handler.py` resamples to 16kHz with `scipy.signal.resample_poly` before it reaches `SileroVAD`/`WhisperSTT`, which both hard-assume exactly 16kHz.
Tradeoff: browsers don't reliably honor a requested `AudioContext({sampleRate: 16000})` across devices/OSes — the actual capture rate can silently differ from what was requested, and there's no way to verify it from JS. Hand-rolling resampling in client JS (linear interpolation or similar) would be lower quality and, unlike the Python side, untestable with this project's existing pytest setup. Centralizing it server-side keeps all DSP next to the VAD/STT code that already assumes 16kHz, using a real polyphase resampler (`scipy.signal.resample_poly`, exact rational ratio via `math.gcd` of the two rates) rather than a naive one. Cost: one small new dependency (`scipy`, previously only transitive) and a per-chunk resample on the hot path — negligible next to the guardrail/LLM latency already dominating turn time (see decision 23).

## 28. Fixed: Embedder needs HF_HUB_OFFLINE=1 to actually honor "offline" (Part 8)
Decision: `memory/embeddings.py` now sets `os.environ.setdefault("HF_HUB_OFFLINE", "1")` and `TRANSFORMERS_OFFLINE=1` at the top of the file, before `sentence_transformers` is imported.
Context: network happened to be down while verifying Part 8, and `ConversationPipeline` construction (both the CLI path and the web path — they share the same `build_graph()` call) crashed outright: `Embedder` loads `sentence-transformers/all-MiniLM-L6-v2` via `SentenceTransformer(model_name)`, which — even though the model is already fully downloaded and cached locally from Part 3 — still makes a live HEAD request to huggingface.co to check for an optional PEFT adapter config, and raises instead of falling back to the local cache when that request fails. This directly contradicted CLAUDE.md's explicit "Offline = no runtime network calls" decision — the project had been implicitly relying on network being available at every startup, not just at initial model download time, and nothing surfaced this until network happened to be down twice in the same session (once blocking `uv add scipy`, once crashing the pipeline outright). First flagged here as a documented-but-unfixed gap; fixed immediately after, at Jay's explicit request ("fix the HF_HUB_OFFLINE thingy... do whatever you think is the better design choice").
Tradeoff: placed at the top of `memory/embeddings.py` (module-level, before the problematic import) rather than in `main.py`/`demo/web/app.py`, matching the existing precedent from `audio/stt.py`'s Windows CUDA DLL-path fix (same pattern: a targeted fix living next to the dependency that actually needs it, not duplicated across every entry point). This means it applies automatically to *any* code path that imports `Embedder` — CLI, web, tests, or a future script — without needing to remember to set it again each time. Used `setdefault`, not a hard assignment, so an explicit external override (e.g. forcing a fresh re-download) still works if ever genuinely needed. Verified: a standalone `Embedder(config)` call, the full web server startup, and all 14 of `tests/test_memory.py` now pass with zero manual environment setup and network still down — full suite (76/76) confirmed green immediately after.

## 29. Explicit Ollama keep_alive on native client calls, not a periodic background ping
Decision: `config.yaml`'s `llm` section gains `keep_alive: "30m"`, passed through on both native `ollama.AsyncClient.chat()` call sites (`agent/nodes.py`'s `generate_node` and `extract_memory_node`'s classify call) — overriding Ollama's 5-minute default idle-unload window.
Tradeoff: the alternative (a periodic background task pinging Ollama to keep the model resident indefinitely, mentioned as an option in `docs/latency_report.md`'s Part 4 notes) adds a background task with its own lifecycle to manage, for a problem this project doesn't actually have at its current scale — a single-user demo/grading session, not an unattended long-running service. `keep_alive` is a documented, first-class field on Ollama's chat API (confirmed via `ollama.AsyncClient.chat`'s signature) — one line per call site, no new moving parts. Verified directly: triggered a real `generate_node` call and checked Ollama's `/api/ps` endpoint, confirming the loaded model's `expires_at` moved from the ~5-minute default to ~30 minutes out. Chose a bounded 30-minute value over `-1` (never unload) deliberately — comfortably covers a recording session or grading pause without leaving the model permanently resident in VRAM if the whole process sits idle for hours.
Known limitation, not fixed: the input/output guardrail checks go through NeMo Guardrails' own Ollama client (the OpenAI-compatible `/v1/chat/completions` route, not the native `ollama` Python client), which has no equivalent `keep_alive` passthrough confirmed working. Since Ollama's idle timer is per-loaded-model and reset by *any* request to it, a guardrail call landing after `generate_node`'s call in the same turn could plausibly reset the model back toward Ollama's own shorter default rather than preserving the full 30 minutes — not confirmed either way. In practice this only matters for gaps longer than Ollama's own default (5 min) but shorter than 30 min between turns; genuinely long pauses are covered by whichever call happens to run first after the gap picking up the cold-start cost regardless of any keep_alive setting, since keep_alive only affects how long a model stays loaded *after* a response, not whether a given call itself is warm or cold.

## 30. ConversationPipeline.close() waits for in-flight memory-extraction tasks before releasing resources
Decision: `agent/nodes.py` gains `wait_for_background_tasks(timeout=5.0)`, awaited from `ConversationPipeline.close()` (now `async`) before it closes the audio manager. Both call sites — `run_forever()`'s shutdown path (CLI/Ctrl+C) and `demo/web/app.py`'s `lifespan` shutdown (web server stop) — now `await pipeline.close()`.
Context: Jay reported long-term memory never recalling facts across separate web sessions. Diagnosis (real components, no mocks, per this project's standing testing philosophy): checked `data/memory/facts.sqlite` directly and found zero rows despite multiple real conversations — a storage problem, not a retrieval-threshold problem. Ran a controlled test through the actual running web server (stating "my name is Jay and I work as a machine learning engineer," leaving the server process alive afterward instead of killing it): the fact was stored correctly, and a *separate, later* WebSocket session correctly recalled it in a 3-sentence spoken answer ("You work as a machine learning engineer, right? That means you design, build, and implement..."). This proved extraction, storage, and retrieval all work correctly — the missing piece was purely that `extract_memory_node`'s write is fire-and-forget (Part 3's design, ~0.5-1s background LLM call), and nothing previously made the process wait for it before exiting. Stopping the server shortly after a turn (very plausible with `uvicorn --reload` during iterative testing) kills that write mid-flight, silently losing the fact with no error surfaced anywhere.
Tradeoff: bounded by a 5s timeout so a genuinely stuck extraction call can't hang shutdown indefinitely — logs a warning and proceeds anyway if a task is still pending past that. Verified the fix directly, not just by inference: built an isolated pipeline instance, stated a fact, and called `close()` *immediately* with no artificial delay — confirmed the fact was present in the temp store afterward. In practice this safety net matters most for short/fast turns or an abrupt shutdown mid-generation; for longer responses, the background task usually finishes on its own during the several seconds of real-time TTS playback anyway, so `_background_tasks` is often already empty by the time `close()` runs — that's expected, not a sign the fix isn't doing anything, and was confirmed as the normal case during testing. Known residual, unrelated to this fix: the extraction classifier itself sometimes judges a genuinely memorable statement as not worth storing (observed directly: "my favorite programming language is Rust" was classified as `NONE`) — this is the same, already-documented Part 3/decision-9 small-model classifier limitation, not something this fix addresses or was asked to address.

## 31. Extraction now extracts every distinct fact per turn, not just "the single most important one"
Decision: `agent/prompts.py`'s `EXTRACTION_SYSTEM_PROMPT` rule "If multiple facts are present, extract only the single most important one" is replaced with "extract every one of them," one fact per line. `agent/nodes.py`'s `_classify_and_store` now splits the response on newlines and stores each non-NONE line as a separate fact (`long_term.store_fact()` called once per line), instead of treating the whole response as a single fact string. `num_predict` raised from 60 to 120 tokens to fit multiple lines.
Context: after fixing decision 30 (the fire-and-forget timing bug), Jay reported occupation was reliably remembered but his name never was, across roughly 8 real tests. Root-caused with a direct, repeatable test against the exact real phrase ("Hi, my name is Jay and I work as a machine learning engineer.") at temperature 0: the *original* single-fact rule deterministically extracted only the occupation, 3/3 times — never the name. Swapping the sentence order ("I work as... and my name is Jay") flipped which fact won to the name instead, proving this was a recency/positional bias in which fact the model considered "most important," not a genuine relevance judgment — and it silently discarded whichever fact didn't win, with no error or signal anywhere that information had been dropped. This specifically breaks the single most common way people actually introduce themselves in one breath, which is exactly what Jay kept doing across all 8 tests.
Tradeoff: extracting multiple facts per turn means more storage calls per turn in the (previously rare) case a user states several facts at once — negligible cost given `store_fact()`'s existing near-duplicate detection already prevents runaway growth from repeated statements. Verified directly against 9 cases spanning the original failing phrase (now extracts both facts, 2/2 repeats), single-fact cases (name alone, allergy, preference — still each extract exactly one fact, unaffected), NONE cases (a question, a one-off request — still correctly reject), a 3-fact case (name + occupation + allergy, all three extracted), and the order-swapped case (both facts now extracted regardless of order, closing the recency-bias gap). Then verified through the real pipeline end-to-end: stated both facts in one real spoken turn, closed the process immediately (exercising decision 30's fix too), opened a *separate* pipeline instance against the same store, asked "What is my name?", and got back "Your name is Jay." — full real round trip, not inferred. Full test suite re-confirmed at 76/76 (no existing test exercises the extraction classifier directly — it's validated by ad hoc scripts against the live model, same as Part 3's original tuning, since its output isn't practically deterministic enough for a stable permanent pytest assertion).

## 32. Web path gates mic input during TTS playback to prevent an assistant-talks-to-itself feedback loop
Decision: `demo/web/ws_handler.py`'s `WebSocketAudioIO` gains a `_discard_incoming` flag. `play_audio()` sets it `True` (and it stays `True` across every sentence of that turn's response); `push_chunk()` drops incoming audio outright while it's set, instead of queuing it. `begin_turn()` (already called once per turn) also now clears the flag and drains any chunks left in the queue before the next turn starts listening.
Context: Jay reported the web UI "picking stuff up when i am not even speaking," chaining into "a continuous chain of random answers" — and noted it worked fine before. It did: his earlier successful mic test was through the CLI (`main.py`), and all testing since (memory, keep_alive) had moved to the new Part 8 web UI, a genuinely different audio path. Root cause: the browser streams mic audio to the server *continuously*, including while the speakers are playing the assistant's own response — with no echo cancellation, the mic picks that up. `push_chunk()` queued every incoming chunk unconditionally and nothing ever drained the queue between turns except once at session start, so the assistant's own voice, captured throughout a multi-second response, sat in the queue and got fed to VAD as the "next utterance" the instant listening resumed — which the assistant then dutifully transcribed and replied to, which played more audio, which got picked up again, chaining indefinitely.
Tradeoff: this is a "gate the mic, don't try to cancel the echo" fix — full acoustic echo cancellation is a much larger undertaking (matching playback and captured audio, subtracting the known output signal) that wasn't needed here; simply not listening while the assistant's own voice could be re-entering the mic is sufficient for a half-duplex voice assistant (which this already is — `run_turn()` doesn't support barge-in, a documented Future Expansion Point, not new scope). The CLI path (`AudioManager`) was not touched and isn't believed to share this failure mode to the same degree — it has no separate continuously-running "capture and forward to an unbounded queue" task; unread mic frames during blocking playback just aren't pulled from the OS-level input stream at all rather than being explicitly queued up by client-side JS and network-forwarded, so there's no equivalent backlog to dump all at once. A brief acoustic-tail edge case (residual room echo in the first moment listening resumes) is still theoretically possible in both paths and isn't specifically addressed here — the fix targets the multi-second backlog, which is the dominant, actually-reported failure mode. Verified with a direct unit-level test against the real `WebSocketAudioIO` class (not a mock): confirmed normal chunks queue while listening, chunks pushed during an active `play_audio()` call are dropped rather than queued, the gate stays shut across multiple sentences in one turn, and the next turn's `begin_turn()` clears any leaked backlog and reopens listening — plus a full real multi-turn WebSocket regression run against a freshly started server to confirm ordinary conversation still works unchanged.
