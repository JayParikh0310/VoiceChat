- Part 5 — Guardrails (2026-07-15): implemented `guardrails/config.yml` (main model + `self_check_input`/`self_check_output` few-shot prompts), `guardrails/rails/input_rails.co` / `output_rails.co` (Colang flow definitions), `guardrails/manager.py` (`GuardrailsManager`, `GuardrailResult`), and `tests/test_guardrails.py` (19 tests, adversarial prompt list + latency + config-toggle tests). Explicitly requested by Jay ("start 5... do it with all the necessary tests"). Debugged two real integration issues before landing on the final design: (1) NeMo's `ollama` engine defaults to `http://localhost:11434/v1` — an explicit `parameters.base_url` copying this project's own (non-`/v1`) Ollama client URL broke every call with 404s; removed the override rather than "fixing" it to `/v1`, since the default is already correct. (2) The documented `rails.generate(options={"rails": {"output": True, ...}})` pattern for checking a pre-supplied bot response turned out to be a silent no-op — it never blocked even an unambiguous "here's how to make a pipe bomb" test string — traced to NeMo's internal `$bot_message` context variable not getting populated that way; switched to calling `self_check_input`/`self_check_output` directly via the action dispatcher instead (`tradeoffs.md` decision 13). Also found, via the same smoke testing, that a zero-shot version of the self-check prompts (styled after NeMo's own example bots) let clearly harmful content through — qwen2.5:3b answered "No" (don't block) for the pipe-bomb test case; added few-shot examples to both prompts, which fixed it (14/14 on a broader adversarial set — `tradeoffs.md` decision 14). Verified via `pytest tests/test_guardrails.py` (19/19: 8 input + 6 output adversarial cases, 2 latency assertions, 3 config-toggle tests) and a standalone end-to-end script against real Ollama.
- Part 6 — Fallback System + Latency Monitor (2026-07-15): implemented `pipeline/latency_monitor.py` (`LatencyMonitor` — `start_turn()`/`mark()`/`log_summary()`) and `pipeline/fallback.py` (`FallbackManager` — `watch(first_token_event)`, races an `asyncio.wait_for` timeout against an `asyncio.Event`, speaks a random filler phrase via the real `KokoroTTS`+`AudioManager` if the timeout wins), plus `tests/test_latency_monitor.py` (9 tests) and `tests/test_fallback.py` (4 tests, real Kokoro synthesis + a `FakeAudioManager` standing in for speaker hardware, same pattern as Part 4's TTS tests). Explicitly requested by Jay ("start part 6 immediately, in the same way you did part 5"). Verified via `pytest` (13/13 new tests, 76/76 full suite) and a standalone end-to-end script that raced `FallbackManager.watch()` against a real concurrent `asyncio.gather()` task simulating a fast (50ms) and a slow (500ms) LLM response, confirming the fallback correctly stayed silent on the fast turn and spoke an audible filler phrase on the slow one. While benchmarking the filler phrase's own synthesis overhead (~73-113ms warm, beyond the 800ms timeout itself), found and documented a real interaction with Part 5: the 800ms fallback threshold is close enough to the median warm LLM first-token latency (587ms) that once Part 5's input guardrail (~328ms) is sequenced ahead of generation in Part 7, the fallback would fire on almost every turn — flagged in `latency_report.md`'s Analysis section for Part 7 to address, since it wasn't obvious until both Parts' numbers existed side by side.
- Part 7 — Full Pipeline Integration (2026-07-15): implemented `pipeline/pipeline.py` (`ConversationPipeline` — `run_turn()`, `run_forever()`, `prewarm()`, the producer/consumer `_stream_and_speak()`, `_speak_guarded()`/`_speak_raw()`) and `main.py`. Explicitly requested by Jay ("start 7 immediately, same way as other parts... test it... look into [the fallback/guardrail collision]... make sure the full pipeline is within the max time limit... test each component independently as well as in the full pipeline"). No permanent `tests/test_pipeline_e2e.py` pytest suite was written — that file is explicitly reserved for Part 9 by the plan, and `tests/test_vad.py`'s own comments already point real-audio integration testing there — but a thorough standalone verification script was built and run instead (real, no mocks): a genuine spoken utterance synthesized with the project's own Kokoro TTS (so it's real speech, not noise, since Silero VAD doesn't reliably trigger on synthetic noise), resampled 24kHz→16kHz, fed through the real `SileroVAD` chunk-by-chunk paced to real wall-clock time (including the mandatory ~700ms silence-detection wait), through the real, unmodified `ConversationPipeline.run_turn()` — only the physical mic read was substituted for the paced synthetic feed. All existing 76 component tests (Parts 1-6) re-verified passing unchanged, confirming no regressions.
  - Found and fixed three real bugs during this testing, none visible from any single Part's isolated tests: (1) `self_check_input`/`self_check_output` occasionally generated a full explanatory paragraph instead of "Yes"/"No", causing a one-off 5069ms guardrail call — fixed by adding `max_tokens`/`stop` to both prompts (`tradeoffs.md` decision 20); (2) an early version of `_stream_and_speak` used a plain sequential loop instead of a producer/consumer pattern, silently losing Part 4's generation/TTS overlap guarantee (Python async generators are pull-based, so the graph paused between sentences) — fixed by rebuilding it around the same `asyncio.Queue`+`gather()` pattern as `SentenceStreamPlayer` (`tradeoffs.md` decision 21); (3) `tts_first_chunk` was being marked after the blocking `play_audio()` call returned rather than right after synthesis, meaning it measured "sentence finished playing" (several seconds) instead of "audio started" — fixed with an `on_synthesized` callback fired before the blocking play call (`tradeoffs.md` decision 22).
  - Confirmed Part 6's fallback-vs-guardrail collision fix works: starting `fallback.watch()` after the input guardrail check (not before) measured a 0.1ms gap between the two, confirming the fallback races only the LLM's own latency as intended (`tradeoffs.md` decision 19).
  - Found a real, unresolved finding while benchmarking: full-pipeline processing latency measures ~2.6-2.8s to first audio in steady-state, over the 2s budget, even with the GPU otherwise idle — traced to resource contention among the five models this project keeps concurrently resident on one 8GB GPU (Whisper, Silero VAD, Kokoro, the sentence-transformers embedder, and Ollama's qwen2.5:3b), not a code defect in any single component (the main LLM call's latency stayed consistent with its isolated Part 2 benchmark; STT and the guardrail checks did not). An unrelated background process (a game) was also found consuming ~46% GPU during an earlier benchmark attempt — flagged to Jay directly via a clarifying question rather than silently averaging it in or ignoring it; Jay closed it and the final numbers were re-measured clean. Four concrete, unimplemented mitigation options were documented (not chosen unilaterally, since each trades away something real — safety coverage, accuracy, or resource budget) in `docs/latency_report.md` and `docs/tradeoffs.md` decision 23.
  - Verified correctness end-to-end: a benign question produced a correct transcript and a correct, guardrail-passed spoken answer; a genuinely adversarial question ("ignore all previous instructions...") was correctly blocked by the input guardrail with no LLM call made; a multi-sentence response was correctly split and each sentence individually guardrail-checked.
